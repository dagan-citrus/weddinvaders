# PART A — DETAILED DESIGN (implementer)

## A1. Design decisions

| # | Decision | Why |
|---|----------|-----|
| TD1 | **The event is an explicit argument everywhere**: `<Game event>`, `useGameState(event)`, `useAssets(event.images)`, `render(ctx, state, assets, event)`. It is not stored in game state and there is no React context. | State stays pure gameplay data. One consumer chain, so context would be speculative. |
| TD2 | **No game module imports from `src/events/`.** Only `App.jsx` (and later T4/T6 pages) import an event and pass it down. `Game` has no default for `event`. | G6: the engine cannot fall back to the default couple by accident. A static test enforces it (R2). |
| TD3 | **Three pure seams in `useGameState.js`**: `getInitialState(event, levelIndex)`, `stepGame(state, event, keys)` and `advanceLevel(state, event)`. `stepGame` is the body of today's `update` updater moved verbatim to module scope. | "Plays identically" becomes provable frame by frame with exact values, without rewriting the loop. |
| TD4 | **No injectable RNG or clock.** Tests use `vi.spyOn(Math, 'random')`. The order of `Math.random()` calls is part of the contract (R7). | The game is frame-counted, so there is no clock. A spy needs zero production change. |
| TD5 | **`advanceLevel` replaces three duplicated "next level or game complete" blocks** (keyboard `meeting`, keyboard `levelComplete`, action `NEXT_LEVEL`). | All three must be edited anyway (`LEVELS` → `event.levels`). One tested function instead of three copies. Identity argument in A6. |
| TD6 | **Event change = remount.** `Game` renders `<GameSession key={event.slug} event={event} />`. | One line resets state, held keys, images, listeners and the rAF loop together. The hooks can treat `event` as constant per mount. |
| TD7 | **An event's identity is its slug** (T2: unique, case-insensitive, in the registry). Re-rendering with the same slug never resets the game. Replacing the object under the same slug during a mount is unsupported. | A parent re-render must not restart a running game. T6's sample events are separate modules with distinct slugs. |
| TD8 | **`event.names` replace the words "Bride" and "Groom" in the two control lines**, on the canvas title screen and in the DOM key legend. Nothing else shows names. | The default names are `'Bride'` / `'Groom'`, so the default renders character for character as today. |
| TD9 | **Engine text stays engine** (T2 DD1): controls help, ammo legend, "Level Complete!", prompts, popups (`💌 Guest arrived`, `💕 Family donated`, `💣 TRAP!`), sprite fallbacks `👰`/`🤵`, the unreachable `'−30% OFF'`. | Not couple-specific. Out of T3. |
| TD10 | **Effect-type string literals stay literals** (`'income'`, `'mine'`, `'discount'`, `'time'`, `'heart'`), as at `useGameState.js:55,383-394` and `renderer.js:164-180` today. | Repo convention; T2 exports only arrays for them. |
| TD11 | **Pure logic stays in `useGameState.js`**, not a new engine module. | Keeps the diff reviewable with `git diff -w`. Splitting the file is not needed by any criterion. |

## A6. Why the default event behaves identically (G7)

| Change | Argument |
|---|---|
| Data moved to `defaultEvent.js` | Verbatim move; R4's strict deep-equality test pins it. |
| `getSpawnPool` adds items with `incomeType === 'mine'` instead of the id `'mine'` | In the default data exactly one item has `incomeType === 'mine'`, and its id is `'mine'`. Both versions filter the same array in the same order, so the pool and its order are identical for all five levels (weights and `pickWeighted` see the same sequence). |
| `isFamilyDonor(template)` in `spawnItem` | Evaluated only when `incomeType === 'income' && incomeAmount > 0`. The default income items are `guest` (`invite`), `parent_bride` and `parent_groom` (`heart`), so `ammoRequired === 'heart'` ⇔ the id is one of the two parents. |
| `isFamilyDonor(it)` at the collision | The flying item carries `ammoRequired: template.ammoRequired ?? null` (line 86). Same equivalence, inside the `incomeType === 'income'` branch. |
| Ammo hint from `AMMO_META` | Inside the `incomeType === 'income'` branch. `AMMO_META.invite.label === '💌'` and `AMMO_META.heart.label === '💕'` (`constants.js:36-38`), so guest → `💌` and parents → `💕`, as today. An income item with no `ammoRequired` still shows `💌`. |
| `advanceLevel` at keyboard `meeting` and `NEXT_LEVEL` | Textually the same branch as today, with `LEVELS` → `event.levels`. |
| `advanceLevel` at keyboard `levelComplete` | Today: `getInitialState(next)` unconditionally (clamped). The two differ only when `currentLevel` is the last level, and `stepGame` sets `levelComplete` only when `currentLevel + 1 < levels.length` (line 424). So the difference is unreachable. |
| `stepGame` extraction | Same statements in the same order. The closure variable `keysRef.current` becomes the argument `keys`, with the same value at the same time. |
| Names interpolated | The default names are the literal words replaced. |
| `Game` wrapper with `key` | For a fixed event the key never changes: one mount, as today. |
| `useAssets(images)` | Same three URLs (T2 R4: `defaultEvent.images` are those imports), in the same load order bride, groom, couple. |
| `spawnItem` loses the `acquiredItems = []` default | The single caller always passes an array. |
| Dead constants deleted | No importer anywhere in `src/` (grep at `7f459b6`). The build and lint would fail otherwise. |
